# Telegram-міст для Meshtastic

Двосторонній міст між мережею Meshtastic і Telegram: повідомлення з мережі приходять вам у Telegram, а відповіді й команди з
Telegram йдуть у мережу через ваш вузол. Працює як служба `mesh-telegram` на Raspberry Pi з вузлом (не в Docker, не в
веб-панелі). Код: [mesh-telegram-bridge.py](mesh-telegram-bridge.py), інсталятор: [install.sh](install.sh).

```
Meshtastic-мережа ◄─радіо─► вузол (meshtasticd) ◄─TCP 4403─ mesh-proxy ◄─ міст ─► api.telegram.org ─► ваш Telegram
                                      │                                      ▲
                                      └── mesh-logger пише базу ─────────────┘  (міст читає нові рядки)
```

## Що вміє

**З мережі в Telegram** (автоматично): нові приватні повідомлення (завжди), повідомлення з каналу (якщо `TG_CHANNEL=1`),
а також сповіщення, які фіксує логер (наприклад, новий вузол). Вузли, відомі лише через MQTT-міст, не рахуються.

**З Telegram у мережу** (лише з вашого чату `TG_CHAT_ID`):

| Дія | Що відбувається |
|---|---|
| Відповісти (reply) на повідомлення бота | відповідь піде тому ж відправнику: приватно, якщо повідомлення було приватним, або в канал |
| `/ch <текст>` | повідомлення в канал LongFast |
| `/dm <назва> <текст>` | приватне повідомлення вузлу за короткою чи довгою назвою |
| `/nodes` | хто зараз на зв'язку |
| `/status` | короткий стан мережі |
| `/help` | підказка |

Усе, що ви надіслали з Telegram, міст записує й у базу логера, тож це видно й на екрані Pi.

## Вимоги

На Pi з вузлом уже мають працювати:

- `meshtasticd` і **`mesh-proxy`** (порт `4403` роздає потік вузла кільком клієнтам; міст підключається як один із них);
- **`mesh-logger`**: він пише SQLite-базу (`~/.local/share/mesh/messages.db`, таблиці `messages` і `events`), яку читає міст;
- Python 3 і venv `~/mesh-bridge-venv` з бібліотекою `meshtastic`;
- вихід в інтернет до `api.telegram.org`.

> Проксі та логер зараз лежать у вашому основному репозиторії (`scripts/mesh-proxy.py`, `scripts/mesh-logger.py`) і в цьому
> репозиторії їх немає. Без них міст не запрацює: він не читає радіо сам, а бере повідомлення з бази логера.

## Створення бота

1. У Telegram відкрийте **@BotFather** → `/newbot` → назва й ім'я → він видасть **токен** (рядок виду `123456:ABC…`).
2. Напишіть своєму новому боту будь-що (він має «побачити» ваш чат).
3. Дізнайтесь **chat id**: відкрийте в браузері `https://api.telegram.org/bot<ТОКЕН>/getUpdates` і знайдіть
   `"chat":{"id": …}`: це число й потрібне.

Токен це пароль до бота: нікому його не показуйте й не вставляйте в чати та репозиторії.

## Встановлення

```bash
# 1. оточення (один раз)
python3 -m venv ~/mesh-bridge-venv
~/mesh-bridge-venv/bin/pip install meshtastic

# 2. файли на Pi (з цього репозиторію)
scp mesh-telegram-bridge.py install.sh <користувач>@<адреса-Pi>:~/
ssh <користувач>@<адреса-Pi> 'mv ~/install.sh ~/mesh-telegram-install.sh'

# 3. служба (запитає токен, chat id і чи пересилати канал; токен вводиться приховано)
ssh -t <користувач>@<адреса-Pi> 'sudo bash ~/mesh-telegram-install.sh'
```

Інсталятор створює `/etc/mesh-telegram/env` (права 600, читає лише root), службу `/etc/systemd/system/mesh-telegram.service`
(`Restart=always`), вмикає її й надсилає в чат «✅ Mesh-міст запущено». Якщо це повідомлення прийшло, усе працює.

## Налаштування

Змінні в `/etc/mesh-telegram/env` (після зміни: `sudo systemctl restart mesh-telegram`):

| Змінна | Типово | Призначення |
|---|---|---|
| `TG_TOKEN`, `TG_CHAT_ID` | (обов'язкові) | токен бота й єдиний чат, якому дозволено керувати мережею |
| `TG_CHANNEL` | `1` | `1`: пересилати й повідомлення каналу, `0`: лише приватні й сповіщення |
| `MESH_HOST`, `MESH_PORT` | `127.0.0.1`, `4403` | адреса проксі (порт TCP API вузла) |
| `MESH_DB` | `~/.local/share/mesh/messages.db` | база логера |
| `TG_STATE` | `~/.local/share/mesh/telegram-state.json` | до якого рядка вже пересилали (щоб не дублювати після перезапуску) |
| `TG_BACKFILL` | `0` | на порожньому стані: скільки останніх рядків надіслати одразу |
| `TG_DRY` | не задано | `1`: друкувати в журнал замість відправки в Telegram (перевірка) |

## Керування й діагностика

```bash
systemctl status mesh-telegram            # чи працює
sudo journalctl -u mesh-telegram -n 50    # журнал
sudo systemctl restart mesh-telegram      # перезапуск (після оновлення файла чи змін у env)
```

Типові випадки:

| Симптом | Причина |
|---|---|
| Служба `active`, але у Telegram тиша | логер не пише в базу (`systemctl status mesh-logger`), або `MESH_DB` вказує не туди |
| Команди з Telegram «ігноруються» | вони надіслані не з чату `TG_CHAT_ID`: міст відповідає лише йому |
| `✗ помилка: …` у відповідь на команду | немає зв'язку з проксі (`MESH_HOST`/`MESH_PORT`) або вузол не знайдено за назвою |
| Дублі після перезапуску | втрачено `TG_STATE` (файл стану): міст перешле останні рядки знову |

## Оновлення

Скопіюйте нову версію `mesh-telegram-bridge.py` у `~/` на Pi й перезапустіть службу (`sudo systemctl restart mesh-telegram`).
Токен у цьому не бере участі й лишається в `/etc/mesh-telegram/env`.

## Безпека

- Токен і chat id лежать тільки в `/etc/mesh-telegram/env` (600). У цьому репозиторії секретів немає, а інсталятор запитує
  токен приховано.
- Міст слухає **лише один чат**. Хто знає токен, може писати боту, але команди й відповіді прийматимуться лише з `TG_CHAT_ID`.
- Приватні повідомлення з мережі теж приходять у Telegram, а його сервери бачать їх у відкритому вигляді. Якщо це неприйнятно,
  поставте `TG_CHANNEL=0` і не користуйтесь мостом для чутливих розмов.
- Якщо токен потрапив не туди: у @BotFather виконайте `/revoke`, а потім запишіть новий токен у `/etc/mesh-telegram/env` і
  перезапустіть службу.

## Зв'язок із веб-панеллю

Міст і [веб-панель](../README.md) незалежні: панель працює на сервері в Docker і веде власну історію кожного вузла, а міст
живе на Pi й читає базу логера. Обидва бачать ту саму мережу, але міст підключений лише до вашого основного вузла (Pi), а
вибір вузла в панелі на нього не впливає.
